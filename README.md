# WindPilot — почасовой прогноз мощности двух ветротурбин

MVP команды Entropy для HackAlemAI. Система получает архивный выпуск погоды, проверяет доступность данных на момент расчёта, запускает ML-модель, сохраняет прогноз на 24/48 часов и анализирует результат. При изменении входов создаётся новая версия; при неизменных входах используется сохранённая. Это агент с явными правилами и последовательностью действий, без LLM и управления оборудованием.

## Дашборд

Откройте [dashboard.html](dashboard.html) напрямую: это один самодостаточный HTML-файл с инлайн CSS/JS и **58 сохранёнными реальными расчётами** (29 моментов с 31 января по 28 февраля × горизонты 24/48 часов). Моки и внешние CDN не используются. Автономный режим явно обозначен; живой прогноз в нём недоступен.

Для подключения к API и текущей погоде:

```powershell
.\.venv\Scripts\python.exe -m uvicorn windpilot.api:app --host 127.0.0.1 --port 8000 --workers 1
```

Откройте **http://127.0.0.1:8000/**. Дашборд включает:

- прогноз для одной или двух турбин, переключение 24/48 часов, подсказки по часам;
- дневной таймлайн **моментов запуска** в 23:00, наивный бейзлайн с датой последнего измерения и скачивание CSV выбранной турбины/горизонта;
- реальные отметки шагов агента, время HTTP-запроса и явное обозначение повторного использования сохранённого результата;
- январские MAE/RMSE из существующего отчёта и сравнение только с проверенным наивным бейзлайном;
- отдельную кнопку живого прогноза через текущий Open-Meteo Forecast API, помеченного демонстрационным режимом.

Оформление: синий акцент HackAlem, переключатель светлой/тёмной темы рядом со статусом погоды (выбор хранится в `localStorage`), лёгкие декоративные линии ветра с поддержкой `prefers-reduced-motion`. Календарь ограничен 28.02.2026; подсказка объясняет переход в живой режим. Кнопка «Посмотреть шаги агента» открывает прежний фактический журнал; LLM-чат не добавлен.

### Публичный сервис Render

Готов [render.yaml](render.yaml) для **одного Python Web Service на плане Free**: API и HTML обслуживает FastAPI. [Инструкция публикации и проверки](deployment/README.md). Модели, погодный кэш и сохранённые расчёты включены в `deployment/runtime.zip` с контрольными суммами; сборка восстанавливает их без обучения и путей к локальному диску. На Free новые живые расчёты могут теряться при перезапуске — постоянный диск не подключён.

Проверка переносимости: `python scripts/check_deployment_bundle.py` воспроизводит 58 исторических расчётов в изолированной папке и сравнивает их с сохранёнными прогнозами. Публичная ссылка и проверка с другого устройства пока ожидают создания Blueprint в аккаунте Render; локальные тесты не считаются подтверждением публичного деплоя.

Исторический сценарий использует прежний `run_forecast()`; веса модели не менялись. Ветер в живом режиме также запрашивается на 100 м, температура на 2 м, модель источника — ECMWF IFS. Это демонстрация работы на текущих входах, а не подтверждённая точность за пределами января. Время инициализации живой API не сообщает: поле `weather_issued_at` возвращается `null`, бейдж возраста скрыт. При сетевой ошибке живой прогноз не подменяется архивом.

«Онлайн/Офлайн» относится к проверенному доступу к погодному источнику через `/weather/status`, а не к энергосистеме. При открытии файла напрямую показывается офлайн-режим. Дата на шкале — **дата момента прогноза**; API `/forecast?date=...` по-прежнему принимает первый целевой день, поэтому интерфейс передаёт следующий календарный день.

Для обновления встроенного набора сохранённых расчётов после изменения модели:

```powershell
.\.venv\Scripts\python.exe -m windpilot fetch-weather --start 2026-02-01 --end 2026-03-01
.\.venv\Scripts\python.exe -m windpilot.export_dashboard
```

Экспорт использует `TestClient` (нужен `httpx` из `requirements-diagnostics.txt`) и записывает только HTML и отдельные результаты `artifacts/dashboard_runs/`. Модели не переобучаются.

Проверка интерфейса без браузера: `npm.cmd install --prefix artifacts/ui_checks jsdom --no-audit --no-fund`, затем `node tests/dashboard.test.cjs`. Это DOM-проверка поведения, не визуальная проверка в браузере. CSS включает адаптацию для узкого экрана, но визуальную проверку выполнить не удалось: браузерный коннектор в сессии недоступен.

## Быстрый запуск

Python 3.11. Команды выполняются из корня проекта. Исходные CSV не изменяются.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt

python -m windpilot prepare --turbine-1 "D:\Downloads\Dataset HackAlemAI для участников 11.03.2023-28.02.2026 - turbine 1.csv" --turbine-2 "D:\Downloads\Dataset HackAlemAI для участников 11.03.2023-28.02.2026 - turbine 2.csv"
python -m windpilot fetch-weather --start 2025-10-01 --end 2026-02-28
python -m windpilot train
python -m windpilot forecast --origin "2026-01-31T23:00:00+05:00" --horizon 48 --offline
python -m windpilot replay --start 2026-02-01 --end 2026-02-28 --offline
```

Если обучение и загрузка уже выполнены, достаточно команды `forecast`. Без `--offline` погодный клиент получает отсутствующие в кэше выпуски через интернет. `--refresh` повторно запрашивает выпуск. `--config other.json` указывается перед названием команды.

Цикл автоматического обновления (остановка Ctrl+C):

```powershell
python -m windpilot watch --interval 900
```

Он проверяет данные каждые 15 минут. Изменение часа расчёта, погодного выпуска, значений погоды или модели создаёт новый результат. В историческом режиме можно задать `--origin`; для одного прохода — `--iterations 1`. В режиме текущего времени используется тот же архивный источник с консервативным лагом: это не получение самого свежего выпуска в реальном времени.

## Данные и время

- CSV: март 2023 — **31 января 2026**, факта за февраль нет. Цель — нормализованная средняя мощность от 0 до 1, не энергия в МВт·ч.
- Пользователь подтвердил местное время станции `Asia/Almaty`. Преобразование в UTC учитывает исторические изменения этого пояса. Неоднозначный повторяющийся час при смене пояса исключается, без угадывания смещения.
- `prepare` явно отображает русские названия колонок во внутренние имена. Изменять оригиналы не требуется.
- Час `[timestamp, timestamp + 1 час)` пригоден для обучения только при шести корректных уникальных 10-минутных измерениях. Пропуски не заполняются нулями; все причины исключения записаны в `data/processed/quality.json`.
- Почасовые измерения считаются доступными после конца часа. Запуск в 23:00 использует историю максимум до завершившегося часа 22:00–23:00.
- `forecast_origin` должен содержать смещение. Прогноз начинается со следующего целого часа. Запуск 31 января в 23:00 местного времени выдаёт 1–2 февраля.
- Координаты в `config.json` получены из двух Google Maps ссылок задания. Для близких турбин погодная модель может возвращать одну и ту же расчётную ячейку; это нормально. Координаты запроса и ячейки сохраняются.

## ML и проверка качества

На каждую турбину обучается пара `HistGradientBoostingRegressor`, seed=42, без подбора параметров на тесте:

1. Зависимость мощности от измеренной скорости ветра и температуры — на всей доступной истории до границы обучения.
2. Поправка к этой зависимости — на **архивных прогнозах** ветра на 100 м и температуры на 2 м за октябрь–декабрь. Дополнительные признаки: горизонт и час суток. Высота анемометра станции не дана; поправка частично учитывает различие измеренного и прогнозного ветра, но не устанавливает физическую высоту турбины.

Фиксированная проверочная модель обучена по данным, завершившимся не позже 31.12.2025 23:00 местного времени. Она оценивается на январских целях с архивной погодой, доступной в каждый момент запуска. Результаты — `artifacts/metrics.json` и `validation_predictions.csv`; MAE/RMSE считаются отдельно для каждой турбины и горизонтов 1–24, 25–48 часов.

Базовый прогноз сохраняет последнее полностью наблюдавшееся значение мощности на весь горизонт. Если последнее наблюдение старше трёх часов, сравнение с ним исключается и число таких случаев указывается. Для честного сравнения модель и база дополнительно оцениваются на одних и тех же строках. Пересекающиеся прогнозы учитываются как разные пары «момент запуска / целевой час».

Финальная модель обучена до 31.01.2026 23:00. Она не использует более поздние цели и не может запускаться раньше своей границы обучения. Для января укажите `--model artifacts/validation_model.joblib`. В феврале фактическая мощность не требуется как вход, и метрики не выдумываются.

Полученный результат январского запуска (1464 пары на турбину; с оговорками о происхождении архива ниже):

| Турбина | MAE модели | MAE базового прогноза | RMSE модели | RMSE базового прогноза |
|---|---:|---:|---:|---:|
| 1 | 0,2093 | 0,3413 | 0,2663 | 0,4486 |
| 2 | 0,2083 | 0,3440 | 0,2657 | 0,4544 |

Ошибки указаны в единицах нормализованной мощности. Это результат одной отложенной проверки, не гарантия точности на феврале.

## Погодный источник и воспроизводимость

Источник: [Open-Meteo Single Runs API](https://open-meteo.com/en/docs/single-runs-api), модель `ecmwf_ifs`. Запрашивается определённое время инициализации, ветер в м/с, температура в °C и UTC. API фактической исторической погоды не используется.

**Ограничение доступности:** API задаёт время инициализации, но не подтверждённое время исторической публикации. В MVP используется явно записанное консервативное допущение `available_at = issued_at + 12 часов` и циклы 00/12 UTC. Это не доказательство фактической доступности выпуска тогда. Для строгой проверки организаторами нужно подтвердить правила публикации и происхождение конкретного архива; описание провайдера упоминает hindcasts для части истории IFS. Не утверждайте, что архив независимо подтверждён как исходные оперативные выпуски.

Кэш содержит исходный ответ, параметры запроса, момент скачивания и контрольную сумму. Время скачивания сегодня не выдаётся за время публикации в прошлом. Отсутствующий/неполный выпуск вызывает ошибку. При сетевой ошибке разрешён только кэш того же выпуска и координат. Три ограниченные попытки запроса; никакой подстановки фактической или синтетической погоды.

`data/` и `artifacts/` исключены из Git: они воспроизводятся командами выше. Для полностью автономного показа перенесите эти две папки вместе с репозиторием. Модели joblib загружайте только из доверенного источника.

## Выход и подключение сайта

Каждый запуск создаёт `artifacts/runs/<run_id>/`:

- `forecast.csv`: по 24/48 строк на каждую турбину;
- `weather.csv`: использованные входы и происхождение;
- `analysis.json`: число часов, средняя/минимальная/максимальная мощность, количество ограниченных предсказаний, допущения, сравнение с прошлой версией того же запуска.

Основные поля: `run_id`, `turbine_id`, `forecast_origin`, `valid_at`, `lead_hours`, `power_pred`, `weather_source`, `weather_issued_at`, `weather_available_at`, `model_version`. Все временные метки результата содержат UTC-смещение. Мощность ограничивается диапазоном [0, 1] с учётом числа таких случаев в анализе.

Журнал этапов и ошибок: `artifacts/runs/events.jsonl`. Февральское воспроизведение: `replay_forecasts.csv` и `replay_manifest.json`. Каждый дневной запуск сохраняет полный горизонт, поэтому последние часы могут выходить в март. Для оценки февраля фильтруйте `valid_at` по местному календарю; не удаляйте эти часы из оригинальных запусков.

Участник, делающий веб-сайт, может вызывать Python-функцию и читать готовые CSV/JSON:

```python
from windpilot.common import read_config
from windpilot.agent import run_forecast

result = run_forecast(read_config(), "2026-01-31T23:00:00+05:00", horizon=48, offline=True)
print(result["path"])
```

`status` равен `created` или `reused`. Ошибки входов поднимают `ForecastError`, CLI завершает работу с кодом 2. Запускайте один процесс агента на одну папку результатов.

### HTTP API

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn windpilot.api:app --host 127.0.0.1 --port 8000 --workers 1
```

Запрос: `http://127.0.0.1:8000/forecast?date=2026-02-15&horizon=48&offline=true`.
`date` означает **первый целевой день**, запуск происходит в 23:00 предыдущего дня в `Asia/Almaty`.
`horizon` — 24 или 48. `offline=true` запрещает сетевые запросы; при `offline=false` отсутствующий выпуск загружается.
`refresh=true` обновляет выпуск через сеть, если не задан offline. Январские запросы используют проверочную модель до января.
Ответ JSON содержит `run_id`, `status`, `forecast_origin`, `horizon_hours`, `row_count`, массив `forecast` и `analysis`.
Сохранённые результаты API лежат в `artifacts/api_runs/`. Некорректные параметры дают 422, отсутствие необходимых данных — 503.
Схема и интерактивная документация: `/docs`; проверка процесса: `/health`. Это адаптер к существующему агенту, без изменения алгоритма.

Дополнительные маршруты: `/` — дашборд, `/quality` — реальный январский отчёт, `/weather/status` — проверка доступности Open-Meteo (кэш результата на 60 секунд), `/forecast/live?horizon=48` — текущий демонстрационный прогноз. Исторический ответ дополнен полями `trace`, `request_duration_ms` и `baseline`; прежние поля сохранены. В живом ответе `baseline` пуст: свежих измерений мощности нет. Исторические результаты и демонстрационные живые результаты сохраняются раздельно.

### Январская диагностика

[Полный отчёт по девяти пунктам](reports/january_2026_diagnostics.md) и [график мощности](reports/power_curve_january.png).
Основные модели и исходный январский сплит сохранены. Единственное изменение `predict()` — явный отказ для пропущенных/некорректных признаков.

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-diagnostics.txt
.\.venv\Scripts\python.exe -m windpilot.diagnostics
.\.venv\Scripts\python.exe -m windpilot.predict_checks
```

Если CSV находятся не в `D:/Downloads`, передайте обе опции `--turbine-1 "путь" --turbine-2 "путь"`.
Диагностика сравнивает прежние январские прогнозы, считает смещение, ошибки по режимам мощности, замену прогнозной погоды фактом,
обучающую ошибку и проверяет модели на одинаковых входах. Укороченное обучение выполняется в отдельной папке на временной копии CSV.
`--skip-trim` пропускает только эксперимент с укороченным CSV. Граничный скрипт возвращает код 1 при нарушении ожиданий, не скрывая неудачи.
Числа, контрольные суммы и вспомогательные CSV: `artifacts/diagnostics/`.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Проверяются границы времени, неполные часы, пропуски погоды, будущие погодные выпуски, запрет запуска модели до обучения, 24/48 часов на турбину, переиспользование неизменных входов, сохранение новой версии и API. Синтетические входы используются только в тестах и диагностическом графике, не в рабочих прогнозах.
